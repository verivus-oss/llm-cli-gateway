## advisory research (registry + OSV + upstream diff + provenance)

- Resolved version `4.13.5`, `resolved` `https://registry.npmjs.org/hono/-/hono-4.13.5.tgz`, `dist.integrity` `sha512-O6+/eCYRkzzzy0rPWwKLiGBR1nFuUPZynnwjxN1MBA62NNqbT0wQEzQyK2gSO5yDIDB336sXQleAhOHrzlYyKw==` (matches the committed `package-lock.json`). Sole maintainer `yusukebe`, unchanged across the ledgered range. npm carries a `dist.attestations` record with an SLSA provenance predicate (`https://slsa.dev/provenance/v1`, `https://registry.npmjs.org/-/npm/v1/attestations/hono@4.13.5`).
- Why 4.13.5 rather than the exact-4.12 pin the prior contract used: the prior contract pinned an EXACT 4.12.34 to avoid the 4.13.x minor, because the advisories then live were all fixed at 4.12.34. That is no longer possible. The three advisories below have their fix line at 4.13.5, inside 4.13.x, so clearing them REQUIRES the minor. The override moves from exact 4.12.34 to exact 4.13.5 (still exact, not a caret), and the `release-security-audit.sh` hono FLOOR moves `[4,12,34]` to `[4,13,5]` in lock-step (it reads the lockfile, not the override string).

- GHSA/OSV advisories FIXED by 4.13.5 (osv-scanner flagged all three on 4.12.34; ranges read from `api.osv.dev/v1/vulns/<id>`):
  - GHSA-crvj-82cr-hjcx (CVSS 5.9, CWE-444), affected `[0, 4.13.5)`: the query parser does not stop at a URL fragment, so a `?` after `#` is treated as the start of a query string (interpretation differential with proxies, caches, filters). Reached only through hono request query parsing (`HonoRequest.query`).
  - GHSA-g6gw-c38x-mqfc (CVSS 5.3, CWE-400), affected `< 4.13.5`: `parseBody()` with dot-notation parsing has no nesting-depth bound, so a crafted body can allocate a large object graph (DoS). Dot-notation parsing is NOT enabled by default. Reached only through hono `parseBody()`.
  - GHSA-gqvv-2mrq-wpjv / CVE-2026-84365 (CVSS 6.5, CWE-22), affected `[0, 4.13.4]`: `toSSG()` (static site generation) has an incomplete path-traversal fix; an untrusted `ssgParams` value containing `../` can write build output outside the intended directory. BUILD-TIME only; request-time routing unaffected.

- Applicability to THIS gateway: none of the three affected surfaces is on the gateway runtime path. Search space: `grep -rn "from ['\"]hono" src/` returns nothing (no first-party import of hono), and `npm ls hono` shows the single resolved hono (4.13.5, deduped) reached only transitively through `@modelcontextprotocol/sdk` -> `@hono/node-server@2.0.11`. The gateway's runtime entry into that adapter is the SDK `StreamableHTTPServerTransport` -> `getRequestListener` -> the adapter main entry (`@hono/node-server/dist/index.mjs`), which statically imports exactly one hono submodule, `hono/ws` (`defineWebSocketHelper`, used to build `upgradeWebSocket`); that built module pulls in no other hono code. So on the runtime path the query parser / `HonoRequest` (GHSA-crvj) and `parseBody()` (GHSA-g6gw) are never constructed, and `toSSG()` (GHSA-gqvv) is a separate build-time entry point the runtime path never reaches. `grep -rn "upgradeWebSocket" src/` returns nothing, so even the one loaded helper is never invoked, and the `hono/ws` helper source is byte-identical between 4.12.34 and 4.13.5 (the one path the gateway does load is behaviourally unchanged by the bump). Scope note (found by the codex cross-LLM reviewer, folded in): "exactly one submodule" is a property of the adapter MAIN entry, not of the whole hono distribution. Other hono entry points do exist in the installed closure, the adapter's separate `serve-static` entry imports `hono/utils/mime`, and the SDK declares hono directly and ships a Hono example, but none of these is on the gateway runtime path and none reaches the query parser, `parseBody`, or `toSSG`.
