# Four things that were quietly wrong: llm-cli-gateway 3.1.0

_Published 2026-08-18 by VerivusAI Labs_

3.1.0 is 295 commits on from 3.0.0, and the changelog covers all of it. This
piece covers four of the changes, because in each case the interesting part is
not the fix but what the defect says about a class of assumption that is easy to
carry for months without noticing.

All four came out of running the gateway in anger against seven provider CLIs
that are on independent release schedules and answer to nobody. If you
orchestrate several coding agents from one control plane, you will meet all
four eventually.

## 1. A healthy job that produces no output looks exactly like a hung one

The gateway kills a provider child that stops producing output. That is what
`idleTimeoutMs` is for, and every request tool has exposed it for a long time.
The table backing it looked like this:

```ts
// src/index.ts at v3.0.0 (comment dashes replaced with colons)
const CLI_IDLE_TIMEOUTS: Record<string, number | undefined> = {
  claude: 600_000,  // 10 minutes: only used when outputFormat=stream-json
  codex: 600_000,   // 10 minutes: Codex streams stderr progress
  gemini: 600_000,  // 10 minutes: Gemini streams stdout in real-time
  grok: 600_000,    // 10 minutes: Grok streams stderr/stdout activity in headless mode
  mistral: 600_000, // 10 minutes: Vibe streams stdout/stderr in headless mode
  cursor: 600_000,  // 10 minutes: Cursor Agent can stream stdout in print mode
};
```

Three of those comments are the defect. Under the argv the gateway actually
builds, Antigravity (`agy --print`), Vibe (`vibe -p=`) and Cursor
(`cursor-agent -p`) emit nothing at all until the process exits. Not "a little",
not "buffered in chunks": zero bytes, measured. The timer therefore never
resets, and an idle timeout that never resets is not an idle timeout. It is a
wall-clock cap wearing the wrong name.

We found this the way these things are usually found. A real cross-LLM review
job, the kind that legitimately takes a long time because the reviewer is
reading a diff and half a repository, was killed at exactly 600000 ms of
"inactivity" having produced precisely the zero bytes its own behaviour
predicts. The two observability fields you would reach for to check on it,
`stdoutBytes` and `lastActivityAt`, both stay frozen for the whole run of a
perfectly healthy job on those providers, so neither can distinguish a working
job from a dead one.

The fix is not a bigger number. It is recording, per provider, whether stdout
advances at all, and treating that as a first-class registry fact rather than a
comment. `src/provider-definitions.ts` now carries `outputDiscipline` on all
seven providers:

```ts
outputDiscipline: {
  streaming: "terminal-burst",
  flushesOnSigterm: false,
  evidence:
    "Probed 2026-07-26 under the gateway argv (-p=): zero bytes over a 30s run, " +
    "and SIGTERM produced zero bytes before close. ...",
}
```

The `evidence` field is load-bearing. A test requires it to be longer than 40
characters, and the classification is pinned by an exact seven-entry map, so
nobody can quietly assert that a provider streams because it feels like it
should. Claude, Codex and Grok are `incremental`. Gemini, Mistral, Devin and
Cursor are `terminal-burst`. Claude is the only one of the seven that flushes
anything after SIGTERM.

`resolveIdleTimeout` now derives from that:

```ts
export function resolveIdleTimeout(cli: string, override?: number): number | undefined {
  if (override !== undefined) return override;
  if (emitsOnlyOnExit(cli)) return TERMINAL_BURST_RUNTIME_CAP_MS;
  return CLI_IDLE_TIMEOUTS[cli];
}
```

`TERMINAL_BURST_RUNTIME_CAP_MS` is 3,600,000 ms, the schema maximum. So the
default kill time for gemini, mistral, devin and cursor moves from ten minutes
to an hour, and devin gains a bound where it previously had none at all. That is
a real behaviour change and you should know about it before you upgrade: a
genuinely hung Vibe child will now sit there for an hour rather than ten
minutes. We kept a bound rather than removing it because `checkStalledJobs` only
warns and never kills, so this timer is the only thing standing between you and
an immortal child process.

Two honest caveats. The classification describes the *default* invocation.
Cursor with `outputFormat: "stream-json"` does stream incrementally, and
`resolveIdleTimeout` does not look at `outputFormat`, so for that one
combination the hour behaves as a genuine idle window rather than a runtime cap.
That is tracked as #259 and documented in three places in the source rather than
papered over.

The second caveat is that `flushesOnSigterm` records something you also need to
know and cannot recover later. Cancelling a terminal-burst job yields no usable
answer output at all, because those four CLIs produce zero bytes on SIGTERM as
well. Claude is the opposite case, and it exposed a separate bug fixed in the
same release: it flushes between 1.9 KB and 8.3 KB after SIGTERM, and every byte
of it was being dropped. Cancellation, idle timeout and the output cap all
commit the job's terminal row the moment the signal is requested, but the child
lives on through the grace period, and both durable surfaces refused what it
then wrote. The job store's completion write is fenced to non-terminal rows, so
the close-time replay matched nothing; the flight-recorder write was single-shot.
Late output now lands through a write that touches only stdout, stderr and the
truncation flag, leaving status and error owned by the fenced terminal write,
and only a completion write this instance actually won licenses it, so on a
shared PostgreSQL store one instance cannot clobber a result another already
committed.

The general lesson, if you run agents at scale: check whether your liveness
signal is capable of taking the value that would indicate liveness. Ours was
not, for four providers out of seven, and the comment sitting next to it
asserted the opposite in prose that nothing could falsify.

## 2. Upstream's deprecation cycle is not your review queue

Seven provider CLIs. Between 3.0.0 and 3.1.0 every one of them moved:

| provider | 3.0.0 | 3.1.0 |
|---|---|---|
| claude | 2.1.212 | 2.1.233 |
| codex-cli | 0.144.5 | 0.147.0 |
| Antigravity (`agy`) | 1.1.3 | 1.1.13 |
| grok | 0.2.101 | 1.0.4 |
| vibe | 2.20.0 | 2.24.1 |
| devin | 3000.1.27 | 3000.4.25 |
| cursor-agent | 2026.07.16 | 2026.08.11 |

Grok went from `0.2.x` to `1.0.4` in a month and dropped `--best-of-n` and
`--check` on the way. Devin dropped `--agent-config`. The gateway had a recorded
contract for each CLI's flags and subcommands, so it knew about the drift in
principle. In practice it knew nothing, because the contract was only compared
against reality when a human ran a manual probe, and `doctor` cheerfully printed
`probed: false` alongside a string telling that human to go and do so.

Three separate things changed here, and they solve three different problems.

**Detection.** `src/provider-version-guard.ts` compares installed versions
against the recorded contract, offline, with no I/O of any kind. That comparison
now runs in `doctor` on every invocation, is exposed as a new read-only
`provider_version_guard` tool, and fires once at gateway start, silently unless
something has drifted. You can turn the startup check off with
`LLM_GATEWAY_DISABLE_STARTUP_VERSION_CHECK` set to `1`, `true` or `yes`; it is
on by default.

The unglamorous part of that module is the normalisation, and it is the part
that matters. The seven CLIs cannot agree on whether to print their own name, or
where to put it. These are the strings the installed binaries actually print,
pinned in the test fixture:

```
claude   2.1.233 (Claude Code)      contract: claude 2.1.233
codex    codex-cli 0.147.0          contract: codex-cli 0.147.0
gemini   1.1.13                     contract: 1.1.13
grok     grok 1.0.4 (d846eb93d9)    contract: grok 1.0.4 (d846eb93d9)
mistral  vibe 2.24.1                contract: vibe 2.24.1
devin    devin 3000.4.25 (7e8e528a) contract: devin 3000.4.25 (7e8e528a)
cursor   2026.08.11-e8db854         contract: cursor-agent 2026.08.11-e8db854
```

Claude puts its product name in trailing parentheses, Cursor omits it, and a
naive equality check therefore reports drift on two perfectly correct installs
out of seven. That is worse than no check at all, because a check that cries
wolf gets disabled inside a week. So the guard strips a trailing parenthesised
suffix (keeping it as a build id only when it looks like one), strips a
longest-match product prefix, strips a leading `v`, and compares build ids only
when both sides carry one. It returns `match`, `drift`, `not-installed` or
`unknown`, and only `drift` fails the summary. A probe that fails reports
`unknown` and never `current`.

The fixture is deliberately hand-maintained rather than derived from the
contract, because deriving it would make every match test tautological. The cost
is that a provider upgrade makes it stale, which is exactly how the Antigravity
1.1.7 to 1.1.8 bump surfaced.

**Application.** `npm run providers:rebaseline` probes the installed binaries
and rewrites the contract in place. That much shipped in 3.1.0-rc.1, and it
originally reported flag *removals* for a human to apply, on the reasoning that
a removal has to be made in lock-step across the contract, the argv generator
and the request path.

That reasoning is correct about the coupling and wrong about the conclusion.
The gateway passes through what the installed binary supports and nothing else,
so a provider's deprecation cycle is not something we get a vote on. Making
every vendor deprecation a review item does not add safety, it adds a queue.
`--apply` now deletes the flag from `src/upstream-contracts.ts` and from the
contract-derived generation tables in `src/provider-codegen.ts` in the same run,
along with the comments that described it, and drops stale
`acknowledgedUpstreamFlags` on the same pass. If you genuinely believe a flag is
real but deliberately undocumented, you say so in the contract with
`hiddenFromHelp` and the writer refuses to remove it.

What the tool will not do is rewrite the hand-written argv emission in
`src/index.ts`, because a flag string does not determine which parameter names,
Zod fields and pass-throughs feed it. The devin `--agent-config` removal touched
22 references, none of which spell the flag. So those sites are reported with
`file:line`, and exit code 3 changed meaning to match: it used to mean "a human
must judge an upstream change" and now means "the gateway still references a
flag the installed binary dropped", which is a defect in code we own rather than
news about somebody else's product.

**Consequence for callers.** Two tool schemas lost fields, and this is the
breaking part of 3.1.0. `grok_request` and `grok_request_async` no longer accept
`bestOfN` or `check`. `devin_request` and `devin_request_async` no longer accept
`agentConfig`. If you pass them you now get a schema validation error rather
than a request the provider rejects at argument parsing, which is a better
failure but still a failure you have to fix.

One thing to be clear about, because the release notes could easily imply
otherwise: both removals in this release were applied by hand, before the
auto-apply policy existed. The automation ships covered by unit tests, including
three that exercise the real `src/upstream-contracts.ts` and
`src/provider-codegen.ts` with hypothetical flags, but it has not yet been
exercised against a real in-tree removal. There is also a stale corner:
`scripts/provider-drift-check.sh` and the systemd unit description still carry
the old wording and claim removals are never auto-applied. The code is right and
the shell comment is not.

The scheduled runner (`setup/systemd/gateway-provider-drift.{service,timer}`,
daily at 04:00 with 45 minutes of jitter, offset from the autoupgrade timer) is
entirely opt-in and is not even in the npm tarball: `scripts/` and
`setup/systemd/` sit outside `package.json#files`. If you want a daily drift
check you install it from a source checkout and edit the `ExecStart` path
yourself.

## 3. A gate that checked the engine when the property was ownership

This one is the most instructive, because the guard was doing something
sensible and still had to go.

The gateway can run a provider inside a git worktree it owns and cleans up. 3.0.0
shipped that with a fail-closed rule: PostgreSQL-backed sessions reject
gateway-managed worktrees before creation, because a different database-connected
host cannot safely own a filesystem-local artefact's cleanup. In code that was
one line:

```ts
if (!(runtime.sessionManager instanceof FileSessionManager)) {
  throw new Error("Gateway-managed worktrees require file-backed session persistence ...");
}
```

Nobody noticed, because nobody was on Postgres-backed sessions. The session
store had a selector of its own, `DATABASE_URL`, and nothing set it. So on a
host whose `[persistence].backend` was `"postgres"`, with the job store,
validation runs and durable receipts all on Postgres, the *sessions* quietly
stayed in `~/.llm-cli-gateway/sessions.json`. One database, two ways to select
it, and the subsystem nobody had wired up kept its own file on disk.

3.1.0-rc.5 fixed that: the session store follows `[persistence]`, the same
selector everything else uses. Which immediately made the worktree guard bite
for the first time, on every Postgres host, and `worktree: true` began failing
closed. That candidate was tagged and never published; the defect was found by
an adversarial cross-LLM review of the release, not by the change's own
verification.

The interesting question is what the guard should have been. The hazard it
protects against is real: with a shared store, an instance on another host might
adopt or delete a directory that only exists here. But "is the session manager
file-backed" is a proxy for that, and a bad one. A git worktree is a local
filesystem artefact owned by exactly one **host**, and that property has nothing
to do with which engine stores the session row.

It also turned out the real property was already enforced, independently. Reuse
requires `worktreeOwnerHostname === hostname()` plus a live Git validation of
the on-disk worktree; cleanup runs with `expectedOwnerHostname` and
`requireOwnerMetadata` so a foreign-owned worktree is skipped rather than
removed. The engine check was a second, coarser guard standing in front of a
correct one, and removing it changed nothing about the safety property while
restoring the capability.

`PostgreSQLSessionManager` now implements the cleanup-tombstone query and
finalization surface rather than returning `[]` and `false`, and the hostname
filter is applied in the SQL rather than in the process:

```sql
WHERE metadata->>'worktreeCleanupPendingDeletion' = 'true'
  AND metadata->>'worktreeOwnerHostname' = $1
```

so another host's rows never enter this process at all. Recovery stays lazy and
instance-scoped, with no blanket startup sweep, because on a shared store a
startup sweep attacks other live instances (a defect we already fixed for jobs
in issue #139). And the scoping is by host, not by process instance,
deliberately: the instance id is a fresh UUID per process, so requiring instance
equality would break worktree reuse across an ordinary gateway restart. The
instance id is provenance; the host owns the disk.

That compatibility surface does not make ordinary PostgreSQL deletion durable.
Explicit deletion removes the session row before its cleanup observer runs, so
a failed worktree removal leaves no tombstone for automatic retry. The
database-side `cleanup_expired_sessions` function invokes no gateway observer
and performs no worktree cleanup. Issue #305 tracks durable failed-cleanup retry
for the owning host.

### If you are on Postgres, read this before upgrading

Moving sessions onto `[persistence]` has no opt-in step and no automatic
migration. On a host with `backend = "postgres"`, 3.1.0 reads sessions from
Postgres. The existing `sessions.json` is not read, not migrated and not
deleted, so your prior sessions become invisible until you backfill them. The
backfill is `node dist/migrate-sessions.js`, a manual invocation rather than an
npm script.

If that database was created by the job-store path and `npm run migrate` was
never run against it, the `sessions` table may not exist. The gateway will start
(the connection succeeds) and the first session operation will throw, with the
migration command in the message. `doctor` does not currently detect an orphaned
file store, which is a gap.

The migration itself had a defect worth knowing about, fixed in the same line of
candidates: `FileSessionMigrationRecord` carried no `createdAt` or `lastUsedAt`,
so the import stamped `new Date()` for both and collapsed weeks of history into
a single window. That is silent and entirely downstream: ordering by
`last_used_at` becomes arbitrary, and most-recent-session resolution picks
effectively at random. It does not affect expiry, because the PostgreSQL session
store has no expiry to affect: the 30-day TTL exists only on the file backend,
and the `cleanup_expired_sessions` function in the schema is never invoked by
the gateway. Source
timestamps are now carried and written, and a row whose timestamps cannot be
parsed is rejected rather than imported with the clock's value.

Finally, `DATABASE_URL` survives as a deprecated override that warns once, with
one rule that matters: it is refused when it disagrees with `[persistence].dsn`,
and refused when `[persistence].backend` is explicitly written as `"sqlite"`,
`"memory"` or `"none"`. Honouring it in those cases put sessions in one database
and jobs in another, which is exactly the split the selector exists to remove.
It is still honoured when no `[persistence]` block is configured at all, because
refusing it there would silently move an existing deployment's sessions from
Postgres to an empty file store.

This does not finish the job. Prompt and response bodies stay in SQLite in
`~/.llm-cli-gateway/logs.db` behind a deliberate gate. Three stores become two,
not one.

## 4. "Accepted at parse" does not mean "supported"

The gateway's whole job is to pass through what a provider CLI offers and
nothing else. Its contract file records each flag's accepted values, and that
list is enforced as a **rejection** list before spawn. Which means a value
missing from it is not documentation debt. It is the gateway actively refusing a
capability the binary has.

Cutting this release turned up one of those. grok's contract carried a
five-level enum on `--effort`. The binary carries no such constraint:

```
--reasoning-effort <EFFORT>
    Reasoning effort for reasoning models

    [aliases: --effort]
```

No `[possible values: ...]` line. The contract had enum-locked the **alias** and
left the canonical spelling unconstrained, so the same upstream option was
validated two different ways and a caller could bypass the constraint entirely
by picking the other parameter name. The comment justifying the enum quoted a
help line the binary has never printed.

The interesting part is the probe, because the obvious one is wrong. Passing a
garbage value and watching for an error does not work:

```
grok --reasoning-effort bogus --single
error: a value is required for '--single <PROMPT>' but none was supplied
```

That is an error, and it says nothing about the flag under test. The control is
what makes the probe mean anything:

```
grok --permission-mode bogus --single
error: invalid value 'bogus' for '--permission-mode <MODE>'
  [possible values: default, acceptEdits, auto, dontAsk, bypassPermissions, plan]
```

clap reports enum violations **in preference to** the missing-value error. So
for a flag that has a value set, the enum message wins. The absence of that
message is the signal. Without running the control you cannot distinguish "no
constraint" from "the constraint fired but a different error printed first".

And then the same probe, run on two more flags, gives the opposite answer.
`--compaction-mode nope` is also accepted at parse, which looks identical. It is
not the same case: that flag is hidden from rendered `--help`, and the binary
still carries its documentation. `strings` on the executable recovers it:

```
Compaction mode [summary|transcript|segments]: `summary` (default) adds no
pointer; `transcript` points at the raw transcript; `segments` persists
per-segment markdown to grep. Sets `GROK_COMPACTION_MODE`
```

Three values, matching the contract exactly. That constraint is correct and
stays. An audit that had concluded "accepted at parse, therefore the contract is
wrong" would have deleted it.

Two flags, identical command-line behaviour, opposite verdicts. The
discriminator is not what the parser accepts, it is what the binary documents,
and for a hidden flag the only place that lives is the executable itself. Both
findings are now recorded in the contract next to the flags they describe, along
with the probe that settles which case you are looking at.

A related one in the same pass, from the other direction: gemini was published
as a cost-reporting provider through three separate surfaces, on the strength of
a parser and an extraction path that exist in the tree. Neither is reachable,
because the adapter rejects the output formats they parse before it ever spawns.
A month of production traffic settled it: 0 of 2241 rows carried token counts.
Unreachable code is not a capability, and the fix was to stop claiming it.

## Two smaller things worth knowing

**Publishing authority is now separate from repository execution.** Until this
release a single npm-publish job held `id-token: write`, checked out the
repository, and then ran repository-controlled build, test, audit and packaging
code. That is the same trust shape as the keyv/cacheable incident, where
compromised source published a valid-provenance package through a legitimate
workflow. The workflow is now two jobs: a build job with `contents: read` only,
no OIDC identity and no registry credentials, and a publish job that holds the
identity, checks out nothing, runs no repository script, downloads one artefact
and refuses it unless the SHA-256 matches what the build job produced.

Two failures surfaced while doing that, both worth stealing. First, a GitHub
release created by a workflow using `GITHUB_TOKEN` does not start other
workflows, so a release-from-tag workflow that "triggers publishing" triggers
nothing; 3.1.0-rc.5 was created that way and silently never reached npm. Second,
`npm publish release/pkg.tgz` is parsed by npm-package-arg as a **hosted-git
shorthand**, because `owner/repo` matches before anything examines the `.tgz`
suffix or whether the file exists. The publish failed with
`git@github.com: Permission denied (publickey)` after the tarball had already
downloaded and verified. The fix is one character, `./`, and the workflow's own
dry-run mode cannot catch it, because dry-run skips the step where the spec is
parsed.

**Least-cost routing stopped reading prompt bodies.** `loadLcrPriorRows` bulk
read `requests.prompt` on every load, which was the only production query that
read a prompt body in bulk and the blocker for encrypting those columns at rest.
The estimator touches its text in exactly two ways, `text.length` and
`classifyContent(text)`, so those two signals are now persisted at write time
(flight-recorder migration v11, after redaction) and the estimate is
reconstructed from them at read time. Persisting the signals rather than a
finished estimate is deliberate: the tokenizer multiplier and the calibration
factor are applied from live values, so changing either does not invalidate
anything already stored. A property test over 2000 random inputs asserts exact
equality with the original estimator, with a negative control showing that a
mislabelled content class diverges. Routing itself is still dormant behind
`[least_cost].enabled`, which defaults to `false` and cannot be turned on by any
environment variable.
